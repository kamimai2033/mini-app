# ミニアプリ基盤

HTML・CSS・標準JavaScript（ES Modules）による軽量な道具箱です。Reactなどの実行用フレームワークは使いません。基本ツールは静的配信だけで動作します。画像・音声・PDF・OCR・JAN読取りは端末内で処理し、辞書・百科検索と天気は外部の情報提供元、日用品・衣類は利用者が指定したNASのAPIと通信します。

画面は元のグレーの配色・配置を基本とし、スマホ操作や表示崩れの修正に必要な変更だけ加えています。

## 画面・命名の開発方針

- 上部ナビゲーションの分類名は原則2文字とします（例：勉強・趣味・生活）。
- 同じ階層・同じメニュー内で項目名の文字数を揃えます。「生活」の展開メニューは各6文字、「日用品・衣類」の画面内メニューは各4文字とします。
- メニュー名と画面見出しは同じ名称を使います。既存の固有名や利用者が指定した名称は、改修時に整合を確認します。
- 文字数を揃えるための不要な空白や、入力欄を合わせるための全角スペースは加えず、位置・幅はCSSで調整します。
- 従来の配色と配置を維持します。操作ボタンは標準グレー・角丸なしとし、スマホの操作性と表示崩れの修正に必要な変更を加えます。

追加機能の確定した階層・名称・配置は[生活メニューの画面仕様](docs/life-navigation.md)を参照してください。日用品・衣類連携はv1.9.0、天気予報と雨雲の連携はv1.10.0で実装しました。

## バージョン管理

- 機能追加・大規模な更改：minorを1上げ、patchを0に戻します（例：1.8.4 → 1.9.0）。
- 修正・小規模な調整：patchを1上げます（例：1.9.0 → 1.9.1）。
- 2.xへの移行は別途合意した大きな更改に使います。番号は小数ではなく3要素で扱い、1.9.xの次に1.10.0を使用できます。
- 2.xの候補は[更改案](docs/roadmap-2x.md)を参照してください。現行リリースへの実装確約ではありません。

## 日用品・衣類

「生活 → 日用品・衣類」から、日用管理・衣類管理・通知履歴・共通設定を切り替えます。商品／購入履歴／棚卸し／予測日の補正、種類／衣類／個体状態・期限・延期、通知実行、バックアップ作成・ダウンロード・復元を扱います。

**NAS側にもモバイルAPI対応版が必要です。** 詳細な導入手順と同期仕様は[日用品・衣類の連携](docs/inventory-integration.md)を参照してください。元のAPIだけでは、安全なオフライン再送を開始しません。

## 天気予報くん

「生活 → 天気予報くん」に、地域の予報と雨雲レーダーを同時に表示します。東京23区・神奈川・千葉・埼玉・大阪・札幌・福岡を選択でき、予報はTsukumijima、雨雲は気象庁、背景地図はOpenStreetMapから取得します。既存の外部サービスを使うため、天気用のNAS APIを新設する必要はありません。

初回は東京の代表地点を表示し、位置情報の許可は求めません。「現在地を使用」を押したときに位置情報を取得し、**中心から半径2km（直径4km）の円全体**が入る縮尺に合わせます。現在地の地点別雨量は、既存のCloudflare Workerへ座標を送って取得します。接続先は画面下部の設定で変更でき、空欄で保存すると地点別雨量だけを停止します。

前回の地点は端末に保存し、次回の地図表示にも使います。アプリを開き直した後は、再び「現在地を使用」を押すまで地点別雨量のWorkerへ座標を送りません。Workerの応答はJSONと、従来Workerが返す名前空間付きYDF XMLの両方に対応します。

雨雲の時刻・再生・濃さを操作できます。地図を拡大しても雨雲データ自体の細かさは増えません。予報と地点別雨量は前回取得したテキストを保存しますが、地図・雨雲画像のオフライン表示は保証しません。詳細と配備後の確認項目は[天気の連携](docs/weather-integration.md)を参照してください。

## 配置と更新

- 配信用の`deploy`ブランチ、または生成した`dist/`の中身をHTTPSの静的Webサーバーで配信してください。開発時はlocalhostでも動作します。ルートとサブディレクトリの両方に対応します。
- `index.html`、`service-worker.js`、`scripts/app-config.js` は、サーバー側で長期キャッシュさせないでください。
- 新版のファイル一式を配置します。必須ファイルをすべて保存できた場合だけ新版を待機状態にします。更新失敗時は以前のService Workerとキャッシュを維持します。
- 「新版の準備ができました」と表示されたら、このアプリのすべてのタブとPWAウィンドウを閉じ、開き直してください。開いている画面に強制更新をかけません。
- ブラウザの保存データを消すとオフライン用データも失われます。OSやブラウザによる容量整理でも消える場合があります。
- 既存PWAの識別子を変えないため、`manifest.json` の `id` はローカル版から維持しています。別の配信元で新規運用する場合は、導入前に `id` をその配信先に合わせてください。既存インストールの `id` を変更すると別アプリとして扱われることがあります。
- v1.10.0への更新も従来と同じオリジン（方式・ホスト名・ポート）と配信パスに配置してください。配信元が変わると、端末に保存したNASの接続設定・取得済みデータ・送信待ちをそのまま共有できません。天気追加のために日用品・衣類のAPIや保存先を変更する必要はありません。

## iPhoneのホーム画面アイコン

v1.9.1では`apple-touch-icon.png`をHTMLから明示的に指定する。画像は既存の192pxの雷マーク入りチップと同一内容で、拡大・描き替えは行わない。iPhoneはこの指定をmanifestのアイコンより優先する。ブラウザのタブ用faviconとホーム画面用の指定は別である。

ホーム画面が「ミ」になるのは、画像が使用されずアプリ名の頭文字で代替されている状態。タグ不足だけが原因とは限らず、インストール時の画像取得失敗・配信先の配置・証明書・古いページの保持などを切り分ける必要がある。実機での最終表示は配備後に確認する。

1. `deploy`のv1.9.1一式を、従来と同じURLへ配置し、静的配信を動かす。
2. iPhoneのSafariで、mini-appのURLの末尾に`apple-touch-icon.png`を付けて直接開き、雷マークのチップが表示されることを確認する（例：`https://example.com/mini-app/apple-touch-icon.png`）。`index.html`で終わるURLの場合はその部分を置き換える。
3. Safariでアプリを開き、旧PWAを含む全ウィンドウを閉じてから再度開く。画面がv1.9.1であることを確認する。
4. Safariの「共有 → ホーム画面に追加」で、追加前のプレビューがチップになっているか確認する。
5. 既存の「ミ」のアイコンを置き換える場合も、先に送信待ちを同期し、必要なら端末データを書き出す。新しいアイコンと必要なデータを確認してから旧アイコンを整理する。切り分けの初手でサイトデータを消去しない。

画像自体を直接表示できなければ、HTMLだけ更新しても改善しない。NASでのファイル配置・HTTPS・アクセス権を確認する。iPhoneのインストール処理がService Workerのキャッシュを使うことには依存せず、追加を確認するまでは配信を継続する。

根拠：[WebKitのホーム画面アイコン仕様](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/#new-fallback-icon)。

## 文字認識（OCR）

「勉強 → 文字認識」で「OCRを準備する」を実行します。初回のみ約13MBをjsDelivrから取得します。バージョンとSHA-256を固定し、正常に検証できた認識エンジン・日本語/英語データを保存します。通常のアプリ起動にはOCRのダウンロードは含みません。

準備後はオフラインで画像の文字認識ができます。画像と認識結果は外部へ送信しません。日本語、英語、両言語の混在を選択でき、結果の編集・コピー・テキスト保存ができます。準備や認識を中止できます。準備途中に停止した場合、保存済みファイルから再開します。

画像は1枚20MB・2500万画素まで。処理時は長辺3200pxまで縮小します。印刷された横書き向けで、手書き・縦書き・段組み・小さい文字は誤認識する場合があります。PDF直接入力や複数画像の一括OCRは対象外です。HEICなどブラウザで開けない画像はJPEG/PNGに変換してください。認識結果は原画像で確認してください。

## 各機能の保存・通信

| 機能 | 通信・保存 |
| --- | --- |
| 文字測定、エディ太、メールアドレス生成 | 端末内処理。入力は再読み込みで消えます。 |
| POS | 一時利用用。商品・在庫・取引履歴は再読み込みで消えます。 |
| PDF、音声 | 選択したローカルファイルを端末内で処理します。 |
| OCR | 初回準備のみ通信。認識データはCache Storage、認識結果は画面内のみ。 |
| 日用品・衣類 | 接続先、取得済みデータ、送信待ち、入力中の下書きをIndexedDBに保存。NAS到達時に同期。バックアップ・通知実行は接続時のみ。 |
| 天気予報くん | 外部サービスから予報・地図・雨雲を取得。地域・接続先・前回地点と前回の予報／地点別雨量テキストを端末に保存。前回地点は地図で再利用しますが、開き直した後のWorkerへの座標送信は再度「現在地を使用」を押した後に開始。地図・雨雲画像のオフライン表示は保証しません。 |
| 英英辞書、日日辞書 | Wiktionary/Wikipediaへ検索語を送信します。検索結果はアプリのオフラインキャッシュには保存しません。 |

## 開発・検証

配信サーバーにnpmやNode.jsは不要です。npmは開発時の検証と配信用ファイルの抽出に使います。

```sh
npm ci
npx playwright install chromium
npm run check
npm test
npm run test:ocr
npm run test:inventory
npm run test:weather
npm run test:deploy
npm run build:deploy
```

- `check`: JavaScript構文、全機能の画面・リンク、キャッシュ対象、バージョンの整合確認。
- `test`: 全画面切替、更新履歴、エディタ分離、メール生成、PDF出力、辞書のエラー、320～1280px表示、オフライン再起動、更新失敗・成功、別アプリのキャッシュ保全。
- `test:ocr`: 固定した配布物を検証して取得し、実際の認識エンジンで英語・日本語画像をオフライン認識。結果保存と中止も確認します。
- `test:inventory`: NASとの同期、配信停止後のオフライン起動、応答消失時の再送、競合・復元・依存操作・JAN画像認識を検証します。`INVENTORY_API_SOURCE`にNAS側リポジトリのローカルパスを指定すると、実API＋一時DBでも同じブラウザテストを行います。
- `test:weather`: 天気のデータ処理とブラウザー操作を検査します。外部応答のテスト用データによる確認と、実サービス・iPhoneでの動作確認は区別します。
- `test:deploy`: 一時フォルダで配信ファイルの過不足と内容一致を確認し、必須ファイルが欠けた場合に以前の生成物を維持できることを検証します。
- `build:deploy`: `scripts/app-config.js`の機能・キャッシュ一覧とService Workerから配信に必要なファイルだけを`dist/`へコピーします。圧縮やコード変換はしません。

`tests/.ocr-assets` と `tests/.artifacts` は検証用でGitには含めません。必要なら `OCR_ASSET_DIR` で検証用認識データの場所を指定できます。

機能の登録とバージョン、キャッシュ対象は `scripts/app-config.js` にまとめています。配信ファイルを変更するときは `version` と `package.json`、画面の初期バージョン、CHANGELOGを更新し、同じキャッシュ名で異なるリリースを配らないでください。

## 開発用・配信用ブランチ

| ブランチ | 用途 | 編集方針 |
| --- | --- | --- |
| `main` | 開発用の正本。アプリ本体、検査、説明資料、自動処理を含みます。 | 修正はここ、またはここから分岐した作業ブランチで行います。 |
| `deploy` | 配信に必要なファイルのみ。 | `main`から生成します。直接編集したり、`main`にマージしたりしません。 |

GitHub Actionsは配信用の`dist/`を生成し、その内容でブラウザ・OCR検査を行います。GitHubへの書き込み権限は付与せず、`deploy`への自動pushもしません。手動で検査を再実行する場合はActionsの「Mini-app checks」で「Run workflow」を選び、`main`を指定します。

更新時は`main`を修正して検査を通した後、同じコミットから`npm run build:deploy`で生成した`dist/`の中身で、`deploy`の配信用ファイルを置き換えてコミット・pushします。検査が失敗した版は反映しません。`main`だけを更新しても`deploy`は変わらない点に注意してください。

配信サーバーは`deploy`のルートを公開してください。ビルドコマンドは不要です。GitHubのZIPを使う場合は`deploy`を選んでダウンロードし、展開したフォルダの中身を配置します。手元で生成する場合は`npm run build:deploy`を実行し、`dist/`の中身を配置できます。

Cloudflare PagesやNASの配信元設定は別途`deploy`へ切り替えてください。サーバー内の作業用`.git`ディレクトリは公開対象に含めないでください。

`deploy`には`index.html`、`service-worker.js`、`manifest.json`、`favicon.ico`、`CHANGELOG.md`と必要な`styles/`・`scripts/`・`images/`が入ります。`tests/`・`tools/`・`.github/`・`node_modules/`・npm設定・開発資料は含みません。
