# ニュースくんの連携

対象：v1.12.0。生活メニューの「ニュースくん」から、総合・経済・ITのRSSニュースを読む。本人の複数端末を対象とし、NAS上のFreshRSSを収集・記事・既読・保存状態の正本にする。

## 構成

`各社RSS → FreshRSS + SQLite → ニュースAPI → mini-app`

ニュースAPI、FreshRSS連携、Docker構成、環境変数、起動・検査手順は [services/news](../services/news/) にまとめる。静的なmini-appを更新するだけではRSS収集サービスは起動しない。NAS側を準備してから、画面の接続設定にHTTPSのOriginと本人用アクセスキーを入力する。

FreshRSSを各端末から直接操作する構成にはせず、ニュースAPIが表示用のデータと操作を仲介する。FreshRSSの認証情報・内部連携用キーはNASに保持し、公開JavaScriptへ埋め込まない。mini-appのアクセスキーもメモリー内だけに保持し、開き直した後は再入力する。キーがなくても端末へ保存済みの記事は読める。

既存PWAのURL・manifestのid・scopeを維持する。既存のNAS用HTTPSホストとPWAの配信元は同一とは限らないため、APIでは許可するOriginを明示する。NPMを追加設定するだけで同一Originになったとみなさない。外出先は既存のTailscale経路を使い、新しいWAN公開を必須にしない。

## 初期購読

初期候補はYahoo!ニュースの主要・経済・IT。購読の追加は利用者の操作で行い、mini-appを初めて開くだけでNASの購読先を書き換えない。

設定の「主要を入力」「経済を入力」「ITを入力」でURL・表示名・分野を入力し、「購読先を追加」で登録する。2026-11-15に各URLのHTTP 200、RSS形式、各8記事を確認した。配信内容と提供状況は変わり得る。

| 分野 | 初期候補 |
| --- | --- |
| 総合 | [Yahoo!ニュース・主要](https://news.yahoo.co.jp/rss/topics/top-picks.xml) |
| 経済 | [Yahoo!ニュース・経済](https://news.yahoo.co.jp/rss/topics/business.xml) |
| IT | [Yahoo!ニュース・IT](https://news.yahoo.co.jp/rss/topics/it.xml) |

YahooのトピックスRSSは各カテゴリ最大8件の見出しを提供するため、NASで15分間隔を基本に継続収集する。ただし配信元の更新・制限が優先され、全記事の取得を保証しない。NHK・日本語の日経は、実際に登録する公式URL・更新日時・利用条件を確認して追加する。第三者が生成したフィードを日経公式RSSと表示しない。ITmediaのアプリ組込み条件は採用時に確認する。

根拠：[Yahoo公式RSS案内](https://support.yahoo-net.jp/PccNews/s/article/H000011243)、[RSS一覧](https://news.yahoo.co.jp/rss)、[ITmedia利用条件](https://corp.itmedia.co.jp/media/rss_condition/)。

## 閲覧と保存

- 最初の画面では総合・経済・ITを各最大5件表示し、一覧・未読・保存・カテゴリ・配信元・文字列検索で絞り込む。
- 記事は見出し、媒体または配信元、日時、配信された説明文とリンクで表示し、本文は元サイトで読む。RSS外の本文巡回や有料記事の解除は行わない。
- 同じURLの記事はまとめるが、異なる媒体の記事を見出しの類似だけで消さない。まとめた記事の元IDを保持し、既読・保存操作を対象IDへ反映する。
- 公開日時と取得日時を区別する。古い保存値や配信元のエラーを、最新のニュースがないことと同一視しない。
- 端末には通常記事の直近500件と取得済みの保存記事を保持する。保存記事には別のページングを用い、まだ取得していない過去記事までオフラインで読めるとは表示しない。
- 購読の追加、名称・分類の変更、収集の停止・再開を扱う。初期版は購読・記事データの削除操作を設けない。

## 同期と障害

IndexedDBをPWA配信パス・接続先で分け、他機能の保存領域を変更しない。記事の既読・保存操作は操作UUIDと明示的な状態を端末へ保存してから送る。同じ操作の応答が失われても同じUUIDで再送し、接続回復時に反転操作を繰り返さない。送信待ちがある間は接続先の変更を止める。

NAS識別情報が変わった場合は、以前の送信待ちを別のNASへ自動適用しない。複数タブの送信はWeb Locksで直列化する。未対応環境では操作を保持できるかを案内し、安全な送信を優先する。

ニュースAPIの到達状態、FreshRSSとの同期状態、配信元の取得状態を分けて表示する。API応答が成功しただけで各RSSの取得成功と表示しない。一部の配信元が失敗しても、他のニュースや端末の前回値を維持する。

## 配備と確認

1. NAS側で専用サービス・永続ボリューム・アクセスキー・許可Originを準備する。既存サービスの削除・再作成を伴う入替えは別工程とする。
2. FreshRSS側の定期収集と利用者ごとの取得間隔を設定する。キーを公開リポジトリに保存しない。
3. 同じPWA配信元へ、`build:preserve`で生成した静的ファイル一式を配置する。
4. ニュース画面から接続し、購読・記事・既読・保存状態を確認する。
5. LANとTailscale、iPhoneとPC、オフライン再起動、NAS再起動、配信元エラーを確認する。

初期構成では既存データの自動整理を有効にしない。通常記事30日という保持案は、削除方針を見直す際の設定候補とする。バックアップはFreshRSSの設定・データとニュースAPIの識別情報・操作履歴を対象にする。OPMLだけでは既読や保存状態、操作履歴を復元できない。

自動検査には合成記事・専用プロファイル・テスト用サービスを使用する。NAS実配備とiPhone実機の確認は、ローカル・GitHubの自動検査とは別に扱う。
