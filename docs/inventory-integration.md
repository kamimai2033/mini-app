# 日用品・衣類の連携（v1.9.0）

## 導入順序

1. NASの既存システムでバックアップを作成する。
2. `cloth-daily-administrative`の`main`ブランチ（モバイル連携API対応版）に更新し、既存DATA_DIRを保持してコンテナを再作成する。追加は`GET /api/mobile/snapshot`、`POST /api/mobile/commands`。既存のPC画面・APIは維持する。
3. NASの`ALLOWED_HOSTS`にAPIの実際のホスト名を設定する。`ALLOWED_ORIGINS`には、このPWAを配信する元の**scheme＋host＋port**を完全一致で追加する。パス・ワイルドカードは含めない。PC画面のOriginも残す。
4. 信頼済みHTTPSでAPIへ接続できることを、使用するiPhone／ブラウザで確認する。HTTPSのPWAからHTTPのNASへの接続は使わない。
5. mini-appの`deploy`ブランチの全ファイルを従来と同じURLへ配置する。全画面を閉じて新版を起動する。
6. 「生活 → 日用品・衣類 → 共通設定」にAPIのベースURL（`/api`より前）を保存し、同期を確認する。LANのIPや鍵を配信用ソースへ埋め込まない。
7. 機内モードでPWAを完全に閉じて開き直し、画面・前回データ・JAN読取りを確認する。OCRを使う場合は先にOCRの追加データも準備する。
8. 確認後に停止できるのは**mini-appの静的配信だけ**。NASの在庫APIは動作を継続する。同一サーバーを使う場合はAPIまで停止しない。

配信停止後もPWAのOriginは元のURLのままなので、NAS側の許可Originは残す。更新・再インストール・キャッシュ消失時の復旧には同じOriginで一時的に再配信する。Service Worker、IndexedDB、端末設定が消えた状態での永久起動は保証できない。

## 画面と通信

| 操作 | 接続できる場合 | 接続できない場合 |
| --- | --- | --- |
| 一覧・予測・通知履歴 | NASから取得し端末に保存 | 最後に取得した値と時刻を表示 |
| 商品・購入・棚卸し・種類・衣類・個体の編集 | 端末に待機操作を確定保存後、NASへ送信 | 入力を端末内に保持し、再接続時に送信 |
| 削除 | 共通設定で送信を再確認 | 削除予定だけ保持、接続確認後に再確認 |
| 新規商品→購入、新規種類→衣類 | 先行登録が確定してから順に送信 | 仮IDで依存関係を保持 |
| 新規衣類の個体操作 | 新規登録後に個体IDを取得して利用 | 新規登録が確定するまでは利用不可 |
| 通知チェック・バックアップ・復元 | 送信待ちを解消した状態で実行 | 待機登録せず、接続エラーを表示 |
| JANカメラ・写真読取り | 端末内処理 | 同じ端末内処理。カメラはHTTPS／権限が必要 |

アプリ起動・画面復帰・オンラインイベント・表示中の60秒間隔で、設定済みAPIへの到達を確認する。`navigator.onLine`だけでLAN内かどうかを判断しない。Wi-Fi名やIP範囲を走査しない。iOSでアプリを閉じたままの継続同期は前提にしない。

一覧の既存データはNAS確定値を表示する。未送信の新規商品・種類・衣類は「送信待ち」として別表示し、既存データへの編集内容は共通設定の待機一覧で確認する。オフラインの予測日は前回取得時点の値であり、最新の予測と誤認させない。

入力中のフォームはタブ切替・再読み込み後も保持する。「入力を閉じる」でその下書きを破棄する。別の編集フォームを開く場合は、下書きの置換を確認する。残す場合はキャンセルして先に保存する。

## 再送・競合の仕様

- 1操作にUUIDを付与し、通信開始前にIndexedDBへ保存する。
- NASは更新と受領記録を同じSQLiteトランザクションで確定する。同じID・同じ内容の再送には前回の結果を返す。同じIDで内容が違えば409。
- 商品単位は商品・棚卸し・全購入履歴、衣類単位は衣類・全個体・参照する種類をまとめてハッシュ化する。PC側の既存APIからの変更も検出する。
- 編集開始時の版、または同じ対象への直前の待機操作の確定版と一致したときだけ更新する。異なる場合は409で停止し、勝手に上書き・基準変更しない。
- 衝突した内容を共通設定で確認し、依存する後続操作から取り消して最新データで再入力する。強制上書きボタンは設けない。
- 応答消失で成否不明の操作は取消不可。同一IDで再同期して結果を確定する。未送信・明確な拒否の場合だけ取消可能。
- 削除済みの対象・関係が異なる購入／個体への操作は拒否する。
- NASの復元前に、バックアップに含めない世代IDを変更する。他端末の古い送信待ちは復元後に拒否する。
- 保守状態は閲覧を継続し、待機の送信を停止する。ネットワーク失敗・503で待機操作を捨てない。
- 同一端末のタブ間はIndexedDBの短期リースで送信を調整する。リース失効後の再送もNASの受領記録で重複を防止する。

受領記録の自動削除は行わない。削除すると長期オフライン端末の再送保証を失うため、保持期間の設定は将来設計とする。NASは従来どおり単一ワーカーで動かす。DBファイルを手作業で差し替える運用は対象外で、必ず復元APIを使用する。

## 保存と通知

端末内JSON書出しには、キャッシュ・下書き・待機内容が含まれる。これは内容の確認・手動復旧用であり、自動インポート／再送は実装しない（操作の二重発行を避ける）。保存先は利用者が管理する。

DiscordのWebhookはNASの環境変数のままで、PWAへURLを返さない。PWAは設定済みかどうかと既存の通知日前設定を表示する。通知先の変更は従来どおりNAS側で行う。PWAの通知実行は利用者の確認後だけ行う。

NASへの公開範囲・HTTPS終端・Origin許可は運用側で設定する。LAN外へ公開する機能や自動設定は追加していない。

## 検証

`npm run test:inventory`は公開リポジトリ内のプロトコル用テストサーバーを使用する。実APIとの結合検証は、別途チェックアウトしたNAS側ソースを`INVENTORY_API_SOURCE`に指定し、Python依存を導入して同じテストを実行する。一時DB・通知無効・ローカル専用プロセスを使用し、実NASのデータは使わない。

iPhone実機のカメラ許可、自己署名証明書の信頼、LANアクセス許可、OSによる保存データ削除は実機での確認対象。合成JAN画像でのデコード検証と、実カメラでの撮影条件の確認は区別する。
